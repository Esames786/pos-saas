## 1. Classification rules (as encoded in the manifest header)

1. **Governs `database/migrations/tenant` only.** `database/migrations/edge` is Edge-owned by definition (every file there IS the
   appliance schema; plan classification `EDGE_OWNED`, always RUN); master migrations never run on an appliance.
2. **EDGE_REQUIRED** — the appliance uses the schema directly: the table is a **bootstrap section** (`EdgeLocalBootstrapImporter::PLAN`
   / `EdgeBootstrapService` — the refresh ships WHOLE rows and the importer/applier inserts them as-is, so a column the Cloud adds to
   `products`, `categories`, `combos`, `modifier_groups`, `branches`, `printers`, `receipt_layout_settings`, … MUST exist on the
   appliance before the next refresh or the upsert fails), an **operational** table (`sales_orders`, `shifts`, `print_jobs`, …) or a table
   the shipped runtime / shared cashier path reads (`EDGE_CODE_REFERENCES`, from a grep of `app/Services/Edge`, `app/Http/Controllers/Edge`,
   `app/Models/Edge`, `app/Support`, `routes/edge_runtime.php`, the shared `POSController` / `HeldSaleController` /
   `RestaurantTableSessionController`, `app/Services/{Pos,Sales,Printing,Restaurant,Reports,Finance,Inventory,Customers}` and the POS views,
   with the artifact-excluded Cloud authorities removed).
3. **EDGE_SCHEMA_SAFE** — additive, forward-safe, dependency-safe schema the appliance carries without using it (Cloud-module tables that
   exist empty on the appliance; a shared-table column the appliance never writes; a column another EDGE_REQUIRED migration depends on).
4. **CLOUD_ONLY** — touches only Cloud-module tables, seeds a Cloud-only permission (the appliance's permission graph is rebuilt from the
   Cloud `users` section on every refresh — a seed is never needed there), or references a Cloud-only class. PACKAGE_DECISION is
   always EXCLUDE (SHIP-NO-RUN is rejected by the validator); UPGRADE_TEST is `n/a: CLOUD_ONLY`.
5. **Baseline rule** — every tenant migration in the 0.7.0 release set (`git ls-tree 7b8f886 database/migrations/tenant`, 172 files)
   is the ESTABLISHED appliance schema: every 0.7.0 appliance (the LAB included) already ran all of them. Baseline entries are
   EDGE_REQUIRED when a changed table is used (rule 2), otherwise EDGE_SCHEMA_SAFE. **No baseline entry is CLOUD_ONLY in this manifest
   version**: removing an already-applied migration from the package would make fresh and upgraded appliances diverge (and would break
   later baseline migrations that ALTER those tables); candidates are marked in NOTE for an owner decision (§7).
6. **Destructive / rewrite** — `ADDITIVE_ONLY=false` on any drop (table/column/index/constraint), rename or column change;
   `DATA_REWRITE=true` when existing business rows are UPDATEd/DELETEd (seed inserts and Spatie cache clears do not count). Either sets
   `OWNER_REVIEW_REQUIRED=true` (the validator refuses the entry otherwise).
7. **Dependency safety** — a CLOUD_ONLY migration may never be a prerequisite of a RUN migration. One such chain exists in the 33:
   `2026_10_14_000001_add_cost_of_sales_account_to_categories` (EDGE_REQUIRED, `categories.cogs_account_id`) also adds
   `goods_receipt_lines.cost_account_id AFTER affects_stock`, so `2026_10_06_000001_add_affects_stock_to_goods_receipt_lines` is carried as
   EDGE_SCHEMA_SAFE. Tables whose appliance shape now diverges from the Cloud because CLOUD_ONLY migrations are skipped are listed in the
   manifest `meta.divergent_tables` / `meta.absent_on_appliance` — a future canonical migration that assumes the Cloud shape of one of
   them must be re-checked before it is classified RUN.
8. **Mixed migration** — `2026_10_14_000001_create_online_ordering_tables` adds `products.website_price` / `combos.website_price`
   (bootstrap sections → required) AND creates three Cloud-only tables (`web_settings`, `web_order_routes`, `delivery_zones`) that stay empty
   on the appliance (their models/controllers are excluded from the artifact). Carried as EDGE_REQUIRED; a canonical split is recommended.

## 5. The dry-run plan format (`edge-migration-plan-v1`)

`php artisan edge:local:schema-upgrade --dry-run --json` (and the `plan` member of `edge:local:update … --dry-run --json`):

```json
{
  "format": "edge-migration-plan-v1",
  "manifest_version": "edge-tenant-migration-manifest@2026-10-19.1",
  "entries": [
    {"migration": "2026_10_19_000001_add_medicine_fields_to_products", "group": "tenant", "classification": "EDGE_REQUIRED",
     "decision": "RUN", "tables": ["products"], "owner_review_required": false},
    {"migration": "2026_10_16_000001_add_branding_to_web_settings", "group": "tenant", "classification": "CLOUD_ONLY",
     "decision": "SKIP_CLOUD_ONLY", "tables": ["web_settings"], "owner_review_required": false},
    {"migration": "2026_10_19_000001_add_migration_plan_to_edge_local_updates", "group": "edge", "classification": "EDGE_OWNED",
     "decision": "RUN", "tables": [], "owner_review_required": false}
  ],
  "run": ["…"], "skip": ["…"], "blockers": [],
  "plan_hash": "sha256:<hex>",
  "verdict": "OK",
  "edge_schema_version": "edge-local-schema@2026_10_19_000001_add_migration_plan_to_edge_local_updates",
  "pending": {"tenant": ["…"], "edge": ["…"]}
}
```

- `entries` are in execution order (tenant group sorted by name, then edge); each entry has the stable key order
  `migration, group, classification, decision, tables, owner_review_required`.
- `plan_hash = "sha256:" + sha256(json(["edge-migration-plan-v1", [[migration, group, classification, decision], …]]))` — recomputable
  from the printed entries (`EdgeTenantMigrationManifest::planHash()`), independent of table lists and notes, order-stable.
- `verdict` is `OK` or `RELEASE_BLOCKER` (any `ABORT_UNCLASSIFIED` entry). An unclassified migration is reported as
  `classification: "UNCLASSIFIED"`.
- The human table printed without `--json` has the same rows (migration / group / classification / decision / tables).

## 6. LAB-update rule (owner rule, now mechanical)

1. Build the package; `edge:audit-package` must report `tenant_migration_problems: []` (and `ok: true`).
2. On the appliance (or on a copy of its DB, as in the 0.7.0 pre-install report): `edge:local:update <package.json> <artifact> --dry-run`
   → the exact plan + `PLAN_HASH=sha256:…`. That plan and hash go into the pre-install report the owner approves. The appliance keeps the
   verdict as an `edge_local_updates` row (`result=dry_run`).
3. The approved update: `Update-EdgeAppliance.ps1 -PackageRoot … -ExpectedPlanHash sha256:…` (or `edge:local:update … --expected-plan-hash=`).
   The installer recomputes the plan from the staged new runtime before the switch; **if it differs from the report the update stops**
   (`UPDATE_MIGRATION_PLAN_MISMATCH`, previous version active, nothing switched). A plan with an unclassified migration never installs
   (`UPDATE_MIGRATION_PLAN_BLOCKED`); a non-empty plan without the approved hash never installs (`UPDATE_MIGRATION_PLAN_UNCONFIRMED`).
4. After the switch the new runtime runs exactly the RUN set (one migration per batch, data-loss audited); CLOUD_ONLY files, if any were
   present, appear as `skipped` in the result and in the audit row's `migration_plan`. An EDGE_REQUIRED migration is never silently
   skipped: it is either RUN (and recorded in `migrations`) or the upgrade fails closed and the pointer reverts.

For the next LAB update (0.7.0 → next release, after the canonical merge) the expected plan on the LAB is: the 10 canonical RUN
migrations (§2) + `2026_10_06_000001_edge_phase4_offline_customer_identity` + the Edge migrations since 0.7.0
(`2026_10_04_000001_add_may_approve_pos_to_users_on_edge`, `2026_10_06_000001_edge_phase4_offline_customer_origin`,
`2026_10_19_000001_add_migration_plan_to_edge_local_updates`); no CLOUD_ONLY file can be in the package. The pre-install report must
re-run the dry-run on a copy of the LAB DB and quote the hash.
