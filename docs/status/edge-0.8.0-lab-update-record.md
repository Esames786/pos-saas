## Manager PIN (owner decision 2) — analysis, NOT executed

- Normal UI: `GET/POST /users/{user}/manager-pin` → `TenantUserController::managerPinStore` (route group `auth:tenant` + `tenant.subscription.access` +
  `route.permission` + `prevent.demo.mutation`; permission = the route name `tenant.users.manager-pin.store`). Validation `pin` string 4–64 + `pin_confirmation`;
  storage `ManagerPin::updateOrCreate(['user_id'], ['pin_hash' => Hash::make($pin), 'is_active' => true])` (bcrypt via `Hash`); audit = the row's
  timestamps only (no separate audit log); the PIN never appears in logs (POST body, not query/args).
- The LAB tenant has only the cashier and the approver; neither holds the users-management permission → the UI path needs a LAB login that holds
  `tenant.users.manager-pin.store` (+ `tenant.users.show` to land on the user page). There is no application SERVICE class for PINs — the controller does the work
  inline — so a "service path" would be the same two lines (`Hash::make` + `updateOrCreate`) executed outside the route's authorization, which the owner
  rule forbids as a bypass. **Recommendation:** provision ONE disposable LAB admin login (user with `tenant.users.index/show` and
  `tenant.users.manager-pin.store` only — owner approval needed, it is a third LAB user) and set the PIN through the UI privately; the approver's
  `may_approve_pos` becomes true on the next config refresh (bootstrap v8 users section).

  never write `bootstrap/cache/*.php` into the immutable signed release directory (this is what tripped the audit on 23 Oct).
