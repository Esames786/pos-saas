# EDGE-IDENTITY-1 — canonical cross-system operational identities

Status: **built + MySQL-proven on `feat/14d-2-plan-upgrade-requests` (deploy cloud-safe, Edge dormant).**
Foundation for offline POS + sync. **No offline selling, no sync engine, no ingestion, no Local Mode** —
this sprint only establishes the durable identities by which Cloud and a future Branch Server (Edge) will
agree "this is the same business object" despite different numeric primary keys. `/pos` stays 404;
`activation_ready` stays false; production stays `APP_ROLE=cloud`.

## The problem it solves
Cloud and Edge are separate databases. The same sale may be `id=17` on an Edge appliance and `id=901` once
ingested into Cloud. **Numeric primary keys are therefore LOCAL ONLY** — never the identity by which two
systems recognise the same object. Every sync-relevant operational entity now carries a durable, immutable,
globally-unique **application identity** generated at creation and never regenerated.

## Identity contract

| Entity | Local DB PK | Canonical id field | Format | Generated by | Immutable? | Sync meaning | Display label |
|---|---|---|---|---|---|---|---|
| Sale / check (`sales_orders`) | `id` | `sale_uuid` | ULID | `HasCanonicalIdentity` on create | Yes (guard + unique) | the sale itself | `sale_no` |
| Sale line (`sales_order_lines`) | `id` | `line_uuid` | ULID | trait on create | Yes | a line of a sale | — |
| Payment (`sale_payments`) | `id` | `payment_uuid` | ULID | trait on create | Yes | a payment on a sale | — |
| KOT batch (`kot_batches`) | `id` | `event_uuid` | UUID v4 | model hook (pre-existing) | Yes (guard added) | a sent/printed KOT batch | `sequence_no` (#N) |
| KOT line (`kot_batch_lines`) | `id` | `kot_line_uuid` | ULID | trait on create | Yes | a KOT snapshot line | — |
| Cancellation (`sales_order_line_cancellations`) | `id` | `event_uuid` | UUID v4 | model hook (pre-existing) | Yes (guard added) | a durable cancellation record | Cancel #N |
| Shift (`shifts`) | `id` | `shift_uuid` | ULID | `ShiftService` (pre-existing) | Yes (pre-existing guard) | a terminal shift | — |
| Table session (`restaurant_table_sessions`) | `id` | `session_uuid` | ULID | trait on create | Yes | an open table session | `session_no` |
| Manager approval (`manager_approvals`) | `id` | `approval_uuid` | ULID | trait on create | Yes | an approval record | `approval_no` |
| Customer (`customers`) | `id` | `customer_uuid` | ULID | trait on create | Yes | a customer record | `code` |

Reference/config rows (branches, products, terminals, printers) keep numeric ids from Cloud bootstrap and
are out of scope; the Edge device already carries `edge_devices.public_uuid` (master DB).

## Format decision (locked)
NEW identities use **ULID** (26 chars) to match the already-canonical `shifts.shift_uuid` and the locked
offline `SO-{branch}-{terminal}-{ULID}` sale-number design. The two PRE-EXISTING canonical identities —
`kot_batches.event_uuid` and `sales_order_line_cancellations.event_uuid` — remain **UUID v4**: they shipped
earlier, are already unique+immutable in practice, and the print `logical_key` strings are DERIVED from them,
so converting them would break the deployed print-idempotency contract. That is the one documented format
exception. Single source of truth: `App\Support\Edge\EdgeIdentity` (`REGISTRY` + `REUSED`).

## The `client_uuid` decision (why a NEW `sale_uuid`, not a repurpose)
`sales_orders.client_uuid` was investigated as the sale identity and **rejected** with code evidence: it is a
v4 **idempotency token for one write request**, not a lifecycle-stable identity. It is nullable, tenant-scoped,
and — decisively — **mutable**: a held sale recalled to pay has its `client_uuid` overwritten by the pay
request's key (`SalesOrderController.php` held→pay update path). So `client_uuid` stays exactly as-is (request
dedup), and a new immutable `sale_uuid` is the canonical sale identity. These are **not two ambiguous "sale
UUIDs"** — they have distinct, documented roles, and `sale_uuid` stays constant across the held→pay update
(same row) where `client_uuid` may change.

## Explicit rules
- **Numeric primary keys are LOCAL ONLY.** Foreign keys inside one database keep using numeric ids for
  joins/performance; cross-system relationships resolve by canonical identity (`EdgeIdentityResolver`).
- **Display numbers are NOT sync identities.** `sale_no`, `session_no`, `approval_no`, KOT `#N`, `job_no`,
  receipt no, and timestamps are human/business labels — never synchronise objects by them.
- **Normal HTTP cannot supply a canonical identity.** None of the identity columns are in any model
  `$fillable`, and the trait generates them server-side; a request that posts `sale_uuid=…` is ignored and a
  fresh identity is generated. The only future path allowed to preserve an Edge-minted identity is a trusted
  Edge-sync ingestion boundary — which **does not exist yet** and is not built here.
- **Future trusted sync preserves Edge-created identities.** DB UNIQUE is authoritative; when ingestion is
  built, a re-sent identity will mean "same business object" (idempotent), not "insert another row".

## Generation & immutability
`App\Models\Concerns\HasCanonicalIdentity` — a model declares `$canonicalIdentityColumn` (+ optional
`$canonicalIdentityFormat`, defaulting ULID). On create it generates the identity if absent (so it exists
BEFORE the row is durable — never after printing or during sync). On update it throws if a non-null identity
is changed. All operational rows are created through Eloquent (`::create` / `relation->create`) — verified no
raw-insert path bypasses the trait — so every new row is born with an identity. DB-level UNIQUE indexes
(migration `2026_08_08_000010`) are the authoritative uniqueness guarantee; the trait is the application-level
generate-once + immutability guard (defence-in-depth, not a DB trigger — honestly scoped).

## Migration / backfill (staged, production-safe)
`database/migrations/tenant/2026_08_08_000010_add_canonical_cross_system_identities.php`: for each table,
(1) add the column NULLABLE, (2) idempotent generate-once, memory-bounded backfill (only rows still NULL; each gets a fresh ULID, already-populated rows never change,
batched by id), (3) add the UNIQUE index once every row is populated. The column stays nullable at the DB
level (documented staged step, mirroring the shipped `shifts.shift_uuid` migration): the trait guarantees new
rows are non-null and backfill leaves zero nulls, so a NOT NULL constraint is a later stage — avoiding a risky
whole-table rewrite. Runs only against tenant DBs (edge-only runtime tables live in `database/migrations/edge`
and are untouched). Production census (2026-08-08): all tenants tiny — largest affected table 174 rows, 632
rows total across 7 tenants — so the migration is sub-second and single-pass safe.

## Cross-system resolution
`App\Support\Edge\EdgeIdentityResolver::resolve($modelClass, $identity, $connection)` looks a row up by its
canonical identity on a given connection — a read-only primitive (no ingestion, no writes). Proven by a
two-INDEPENDENT-database test: the same `sale_uuid` under deliberately divergent numeric ids (Cloud id 9000+,
Edge id 1) resolves the correct row on each system, and an Edge line resolves the correct Cloud parent by
identity.

## Bootstrap / Edge compatibility
Because Edge `edge:local:db-init` runs the REAL tenant migrations, these identity columns appear automatically
on future Branch Server local DBs — they belong in normal tenant schema (both Cloud and Edge need them), NOT
in edge-only migrations. No bootstrap version bump: the wire contract is unchanged; the bootstrap package does
not need to ship historical operational rows merely because these columns exist.

## Appliance lifecycle contract (AE — LOCKED now, built later in EDGE-APPLIANCE-UPDATE-BACKUP-1)
The future Windows Bingoo Edge setup/update/backup application is NOT built in this sprint, but its contract
is locked now so no migration ever violates it. Every schema decision here already complies.

- **Normal UPDATE never behaves like NEW INSTALL.** With a valid existing Edge-local DB/binding detected, a
  normal update MUST NEVER `DROP DATABASE` / `TRUNCATE` / `migrate:fresh` / `db:wipe` / reseed operational
  tables / rerun a destructive first-bootstrap / replace the local DB from a Cloud bootstrap / delete unsynced
  operational records. Update uses **forward migrations only**; local sales/payments/shifts/KOT/table-sessions/
  stock events/manager approvals/outbox are durable Edge-origin operational history that must survive updates.
- **Initialise vs upgrade.** The future installer distinguishes an EMPTY/uninitialised DB (initialise tenant
  + edge schema) from an EXISTING valid Edge DB (run ONLY pending forward migrations, preserve all data).
  `edge:local:db-init` and future migration services must keep that distinction; never solve an upgrade with
  `migrate:fresh`.
- **This sprint's migrations are UPDATE-SAFE (AE12):** additive column + idempotent, memory-bounded backfill +
  guarded unique index; no truncate, no `migrate:fresh`, no bootstrap re-import; existing rows preserved;
  safely re-runnable after an interrupted run. Proven by `test_backfill_populates_legacy_nulls_and_is_idempotent`
  (rerun preserves every identity, fills only nulls).
- **Versioned update (AE3):** the future updater decides current→target→required-migration-path from local,
  non-secret state (app/artifact version, tenant+edge schema versions, bootstrap/config revision,
  activation_epoch) without needing internet. `edge:local:status`/`build-info` already surface the runtime/
  activation/bootstrap facts to build on.
- **Mandatory verified pre-update backup (AE4/AE5):** the locked update sequence is DB-health → disk check →
  create backup → verify checksum/manifest → maintenance mode → install files → forward migrate → integrity
  checks → resume. If the backup fails, the update STOPS (no silent "continue anyway"). Backup is a
  transaction-consistent logical dump of the Edge-local DB only (never a casual live-InnoDB file copy), with a
  non-secret manifest (backup format version, created_at UTC, branch/device public ids, activation_epoch,
  app/git/tenant-schema/edge-schema/bootstrap versions, engine/version, file hash).
- **Backup secret boundary (AE6):** a DB backup MUST NOT casually contain `APP_KEY`, `EDGE_LOCAL_APP_KEY`, DB
  passwords, device bearer secrets, private TLS keys, or the Cloud signing private key. `EDGE_LOCAL_APP_KEY`
  stays machine-local. Cross-machine recovery uses the separately-locked KMS-wrapped `DATA_RECOVERY_KEY`
  design (NOT built here). Honestly: a DB backup alone does not authorise a new Branch Server to impersonate
  the old appliance — replacement still requires controlled re-pair/re-provision/re-enrollment.
- **Restore ≠ update; config refresh ≠ restore (AE9/AE10).** Restore is a separate authorized mode (verify
  manifest → compatibility → stop writes → restore → forward-migrate → integrity). An update failure does NOT
  auto-restore. Config refresh uses the already-locked UPSERT-stable-ids + tombstone contract and never wipes
  operational data. Schema migrations are not assumed reversible merely because `down()` exists.
- **Factory Reset / Re-provision** is a completely separate, explicitly-authorized, backup-first dangerous
  recovery action — never reachable through "Update", and not prominent in normal UI.
- **Backup MVP is a release gate before real offline selling:** before a branch is allowed to sell locally,
  at minimum a manual verified "Backup Now" + automatic mandatory pre-update backup must exist.

## Final-proof closure (EDGE-IDENTITY-FINAL-PROOF-1)
Real controller/service integration replaced the earlier model-level mirrors, and it surfaced a genuine
refinement of the contract (this is what real-flow testing is for):

- **Honest line/payment lifecycle (code-proven).** `HeldSaleController::store` does `$sale->lines()->delete()`
  and recreates every line on Add Round / held-edit; `SalesOrderController::store` does the same for
  `lines()` + `payments()` on held→pay. So a line/payment ROW is deleted and recreated on those transitions —
  its `line_uuid`/`payment_uuid` is **stable for a finalized sale and across an idempotent replay, but is NOT
  preserved across a held re-save**. The column values are still immutable (a given row's identity never
  changes); it is the row lifecycle that churns. The durable, lifecycle-stable identity of the check is
  **`sale_uuid`** (the `sales_orders` row is UPDATED, never recreated — stable across hold → add rounds → pay
  and across replay). Proven by `EdgeIdentityFlowMySqlTest` through the REAL controllers (Direct Pay + real
  idempotent replay: same row, no duplicate sale/payment; Add Round: `sale_uuid` stable, lines re-created with
  fresh unique identities; Split: parent `sale_uuid` unchanged, child distinct).
- **Cross-system relationship snapshots (Option B, required by evidence).** Because lines are deleted on
  re-save and the FKs `kot_batch_lines.sales_order_line_id` / `sales_order_line_cancellations.sales_order_
  line_id` are `nullOnDelete`, a KOT line or cancellation would lose its link to the originating sale line —
  and numeric ids are useless across Cloud/Edge anyway. Fix (migration `2026_08_08_000011`): capture the
  originating canonical identity as an **immutable snapshot** at creation time —
  `kot_batch_lines.source_line_uuid` (the source line's `line_uuid`) and
  `sales_order_line_cancellations.source_line_uuid` + `source_kot_event_uuid` (source line + original KOT
  batch). These are reference *copies* (nullable, not uniquely indexed), set once by the trusted service. Proven
  to be captured by the real `PrintJobService`/`KotCancellationService` and to **survive the source line's
  deletion** (`EdgeIdentityFlowMySqlTest`). So a synced KOT/cancellation stays self-contained and cross-system
  resolvable regardless of line churn or divergent numeric ids.
- **Full two-database matrix.** `EdgeIdentityMySqlTest` now resolves ALL ten entities (sale, line, payment,
  shift, table session, approval, KOT batch, KOT line, cancellation, customer) across two genuinely
  independent databases with deliberately divergent numeric ids (Cloud id 9000 / Edge id 1, same canonical
  identity) — and asserts the resolver honours its EXPLICIT connection even when the default connection points
  at the master DB.

## Activation-time schema-hardening gate (NOT NULL)
The identity columns are deliberately left DB-nullable in this sprint (staged; the trait + backfill guarantee
non-null in practice). **Before real Edge activation**, every required canonical operational identity must
either be made DB `NOT NULL`, or have executable proof that every trusted write/ingestion path (including the
future sync ingestion boundary, which does not exist yet) cannot persist NULL. That NOT NULL / no-null-path
proof is a mandatory pre-activation gate, tracked here — do not treat the nullable staging as permanent.

## Backup gate before real offline selling
Restated as a hard release gate (see §AE): **before the first real offline sale / pilot activation,
`EDGE-APPLIANCE-BACKUP-MVP-1` is mandatory** — at minimum manual "Backup Now" + transaction-consistent local
DB backup + manifest/checksum verification + automatic verified pre-update backup (backup failure blocks the
update) + no machine-local secrets in the backup bundle. The full setup/update/restore GUI may come later.
